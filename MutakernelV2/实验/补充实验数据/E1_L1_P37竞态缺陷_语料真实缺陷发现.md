# 语料真实缺陷发现：L1_P37 候选内核缺少 grid 级屏障（竞态）

分类：**独立发现**（与 MutaKernel 的判级结果无关的副产物）。
本文件记录一个 KernelBench 派生候选内核中的真实并发缺陷，
以及它如何被我们的确定性审计发现。

- 主体：`KernelBench/level1/37_FrobeniusNorm_.py` 的 CUDA 候选实现
  （E1 中的内核 ID `L1_P37`，`ModelNew`，`load_inline` 编译的
  `frobenius_norm_kernel`）；
- 缺陷类型：单次 kernel launch 内跨 block 读取部分和，
  **缺少 grid 级屏障** → 数据竞争 → 输出不确定；
- 发现路径：witness 确认协议 WC-1 的判据 (a)（未变异对照复跑）；
- 状态：已实测确认（见 §3、§4）。

## 1. 缺陷位置与机理

内核把整个 Frobenius 归一化融进**一次** launch，分三段：

```cuda
template<typename T>
__global__ void frobenius_norm_kernel(const T* input, T* output,
                                      T* norm, int total_elements) {
    __shared__ T shared_mem[1024];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + threadIdx.x;

    // --- Phase 1: 本 block 的平方和归约 ---
    T local_sum = 0.0;
    int stride = blockDim.x * gridDim.x;
    for (int i = idx; i < total_elements; i += stride) {
        T val = input[i];
        local_sum += val * val;
    }
    shared_mem[tid] = local_sum;
    __syncthreads();
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
        if (tid < s) shared_mem[tid] += shared_mem[tid + s];
        __syncthreads();
    }
    if (tid == 0) {
        norm[blockIdx.x] = shared_mem[0];      // (W) 写本 block 的部分和
    }
    __syncthreads();                            // ← block 内屏障，非 grid 屏障

    // --- Phase 2: 读“全部” block 的部分和 ---
    __shared__ T final_norm;
    if (tid == 0) {
        T total_sum = 0.0;
        for (int i = 0; i < gridDim.x; i++) {
            total_sum += norm[i];              // (R) 读别的 block 的部分和
        }
        final_norm = sqrt(total_sum + 1e-8);
    }
    __syncthreads();
    T inv_norm = 1.0 / final_norm;

    // --- Phase 3: 用本 block 算出的 final_norm 缩放本 block 的切片 ---
    for (int i = idx; i < total_elements; i += stride) {
        output[i] = input[i] * inv_norm;
    }
}
```

启动配置：

```cuda
const int block_size = 1024;
int num_blocks = (total_elements + block_size - 1) / block_size;
num_blocks = min(num_blocks, 1024);            // 上限 1024 个 block
auto block_sums = torch::zeros({num_blocks}, ...);   // 零初始化
```

**缺陷**：`(W)` 与 `(R)` 之间只有 `__syncthreads()`，它是**block 内**屏障。
CUDA 在一次 launch 内不保证不同 block 的执行顺序，也不提供隐式 grid 屏障
（需要第二个 kernel、cooperative groups 的 `grid.sync()`，或原子计数器
自旋屏障）。因此：

1. 先到达 phase 2 的 block 会把尚未写入的 `norm[i]` 读成 **0**
   （`block_sums` 是 `torch::zeros`，所以读到的是 0 而不是垃圾）；
2. 该 block 得到偏小的 `total_sum`，因而偏小的 `final_norm`、
   偏大的 `inv_norm`；
3. phase 3 中**每个 block 用自己算出的 `final_norm` 缩放自己的切片**，
   于是同一次前向的输出里可以并存**多个不同的缩放因子**。

这个缺陷与任何变异无关：**未变异的原候选内核本身就是竞态的。**

### 1.1 为什么它能在均匀随机输入下长期潜伏

上限 1024 个 block，均匀 `rand` 下每个 block 的平方和贡献约占总和的
1/1024 ≈ 0.1%；漏读一个 block 使 `total_sum` 偏小 0.1%，
`final_norm` 偏小约 0.05%，落在 `rtol = atol = 1e-2` 之内。
KernelBench 的 `get_inputs()` 正是 `torch.rand(112, 64, 512, 512)`，
所以标准评测与我们的随机轮都看不到它。

### 1.2 为什么压力策略会把它打出来

E1 的 `sparse_extreme` 策略是 99% 零 + 1% `randn × 1e4`。
此时平方和由极少数巨值主导，这些巨值集中在少数 block 上；
**漏读其中一个 block 就足以把范数挪动百分之几**，直接越过容差。
`boundary_last_element`（只在最后一个元素放极值）同理：该极值所在的
单个 block 决定了整个范数。

这不是"压力策略太苛刻"，而是**压力策略正确地暴露了一个真实缺陷**。
真正需要修的是判级流程对"内核自身不确定"的处理，而不是把策略关掉。

## 2. 最小复现

`_wc_p37_repro.py`（部署于远端 `/root/mk_v2/_wc_p37_repro.py`）不使用
参考实现、不使用容差，用两个**逻辑上无法被舍入解释**的读数证明竞态：

**读数 A（单次前向内可见）**：
`output[i] / input[i]` 恰好等于持有 `i` 的那个 block 所用的 `inv_norm`。
对一次前向的输出统计该比值的**不同取值个数**；
`> 1` 即证明不同 block 用了不同的 `final_norm`，
这只能由缺少 grid 屏障导致。

**读数 B（跨次前向可见）**：
同一输入张量重复前向 8 次，比较输出是否逐比特相同。

两个读数在三种输入分布下各跑一遍：
`uniform_rand`（KernelBench 原分布）、`sparse_extreme`、
`boundary_last_element`；两种形状：生产几何 `(112,64,512,512)` 与
一个小几何 `(2048,1024)`（仍然打满 1024 block 上限）。

配置：`torch` / `cuda` 版本与 GPU 型号写入报告；
输出 `e1/witness_confirmation/p37_race_minimal_repro.json`。

> 实测结果见 §4（审计窗口内串行执行，避免与审计 worker 争 GPU 而污染
> 确定性测量）。

## 3. 证据链（harness 内，2026-07-30）

证据目录：`/root/mk_v2_runs/e1/final_window_review/p37_sync_remove_1_newwitness/`
（9 份 result JSON + `review_summary.json`）。协议：`equiv_runs=0`、
`base_seed=50040`、`stress_policies=["sparse_extreme"]`、`stress_repeats=3`、
`round_timeout=300`，三组各 3 次独立 worker 进程。

| 组 | 内容 | 结果 |
|---|---|---|
| control | 未变异原内核作 candidate | rep1 pass(3/3)、rep2 pass(3/3)、**rep3 在 si=0/seed 50040 发散，max_abs_error 0.017464** |
| witness | `L1_P37__sync_remove__1`（生产 FALSIFIED，witness 在 si=2/seed 50042，max_abs_error 0.0175692） | **9/9 轮全过，witness 0 次复现** |
| lateral | `L1_P37__sync_remove__0`（生产 100/100 全过） | rep1/rep2 pass，**rep3 在 si=1/seed 50041 发散，max_abs_error 0.0292042** |

三条互相印证的事实：

1. 未变异内核自身在同一轮位发散，误差量级（0.0175）与被质疑的 witness
   （0.0176）**完全同级**；
2. 被质疑的 witness 在同一轮位 9 次不复现；
3. 生产中"干净"的同算子邻居反而发散——发散与探针身份无关。

**合并生产与复核的翻车率**：L1_P37 上共 39 个 `sparse_extreme` 轮，
出现 3 次发散 = **7.7%**，分布在原内核 + 两个不同变异体上。
这个数字是 WC-1 协议 `n_A` 选取的经验依据（见预注册文件 §3.1）。

此前已签认作废的旧 witness 轮位 `boundary_last_element / seed 50040`
属于同一机理（单个极值元素所在 block 决定范数）。

## 5. 论文中如何陈述

### 5.1 作为独立发现

建议放在 §5.5（RQ4）的讨论或 artifact appendix，一段话：

> Our determinism audit surfaced a defect in the corpus itself rather than in a
> mutant: the CUDA candidate for KernelBench level-1 problem 37 fuses a
> Frobenius-norm reduction into a single launch and reads every block's partial
> sum after only a block-local `__syncthreads()`, with no grid-level barrier.
> Blocks that reach the second phase early read zero-initialised partial sums,
> so a single forward pass can apply more than one scale factor. Under the
> uniform inputs shipped with the benchmark the error stays inside a 1e-2
> relative tolerance, which is why the kernel passes the standard harness; under
> heavy-tailed stress inputs a single missed block moves the norm out of
> tolerance. We report this as a corpus defect, with a minimal oracle-free
> reproduction, and exclude the affected round positions from mutation
> attribution under the pre-registered protocol of Section X.

这段话对我们是**加分**：它说明我们的压力维度确实能打出真实的并发缺陷，
而且我们的方法学有能力把"内核自身的缺陷"与"变异的效果"分开——
后者正是审稿人会追问的东西。

### 5.2 故障类覆盖降为 4 类的如实陈述

L1_P37 的 5 条 CSE 探针里，`L1_P37__sync_remove__1` 是**CSE 反证阶段
唯一一条 F-SYNC 的 FALSIFIED**。若它按 WC-1 作废，则：

- CSE FALSIFIED 的故障类覆盖由 **5 类**
  （F-RELOP 3、F-ARITH 2、F-INIT 2、F-SYNC 1、F-CONST 1）
  降为 **4 类**（F-SYNC 归零）；
- equiv 侧的 F-SYNC witness（16 条，分布在 12 个内核上）不受影响，
  只要那些内核的对照通过——即 F-SYNC 作为一个**可被检出的故障类**
  在论文中仍有证据支撑，变化只发生在"反证阶段"这一格。

建议表述（不要粉饰、也不要过度自责）：

> Counterexample search falsified the equivalence hypothesis for N of the 453
> probes graded LIKELY_EQUIVALENT, spanning four fault classes. One further
> candidate witness (F-SYNC, kernel L1_P37) was voided by the pre-registered
> confirmation protocol because the unmutated kernel is itself nondeterministic
> at that round position (Section X); F-SYNC therefore has no confirmed
> counterexample in the falsification stage, while it remains represented by M
> confirmed witnesses in the equivalence-challenge stage.

要点：
1. **写清"4 类"而不是含糊说"多类"**；
2. **说明 F-SYNC 归零的原因是审计而非缺检**，并给出 equiv 侧仍有的
   F-SYNC 证据数，避免读者误以为我们的算子打不出同步类缺陷；
3. **不加 policy-skip**：明确声明我们没有为任何内核关闭任何策略，
   处置走的是统一确认协议。

## 6. 上游可报告性

该内核不是我们写的，是语料里的候选实现。修复方式（供上游参考）：
把 phase 2/3 拆成第二个 kernel，或用 cooperative groups
`this_grid().sync()`，或以原子计数器实现自旋 grid 屏障。
我们不修改语料（会破坏 E1 的冻结主体集），只如实记录。
