协议逐条对齐见 `E3_port对齐清单_B9.md`（本文件是其第 5 条"校准执行"的执行侧补充）。

## 1. 为什么需要一次独立的控制校准运行

上游协议（gpuemu，Sarkar 2026）的判定容差不是常量，而是**每个 (op, dtype) 由
正确内核自身的误差分布标定**的产物：以 32 次正确控制的 max-abs 误差取 p95 再
乘 1.5（`calibrate_tolerance`，`E3_port对齐清单_B9.md` 第 5 条）。语料
`meta.json` 里的 fp32 1e-5 / fp16 2e-2 就是上游在其 26-op 语料上跑出来的结果，
不能移植到我们的科目上——`E3_就绪状态.md` 已记录反例：KernelBench L1_P1
（2048³ fp32 矩阵乘）在 1e-5 下 **32/32 FAIL**，而其归约误差约 5e-3 完全属于
正确实现的正常范围；校准后 32/32 PASS。

因此在 B9 参加任何预算匹配对比之前，必须先在**未变异的参考实现**上跑满
32 次控制，逐 (subject, dtype) 得到 `calibrated_tol`。这就是本次校准运行。

**校准单元（unit）定义**：一个 unit = 一个 (KernelBench 任务, dtype) 对，
执行 32 次控制调用。容差按 (task, dtype) 复用于该任务下的全部候选科目——这与
上游"per-(op,dtype) 容差"的口径一致，也是本次运行能以 400 个 unit 覆盖
C2/C3/C5 共 2,032 个科目的原因。

| 项 | 数量 | 来源 |
|----|-----:|------|
| 任务（L1 100 + L2 100） | 200 | `contracts_c2c3c5_draft.jsonl`，sha256 `66c69f7b…1db0` |
| dtype（每任务 fp32 + fp16） | 2 | 契约浮点 dtypes ∩ 已校准集合 |
| **校准 unit 合计** | **400** | `task_table.json`（`gaps: []`，无缺口） |
| 已有有效结果（不再重跑） | 18 | `calibrated_ok` 15 + `calibrated_heavy_tail` 2 + `controls_incomplete` 1 |
| 待重跑（前次失败） | 13 | `run_error`（10 个 quantile 崩溃 + 3 个宿主 OOM） |
| 从未起跑 | 369 | — |
| **队列合计** | **382** | `queue_state.json` |

## 3. `torch.quantile` 缺陷

**现象**：13 个 unit 无结果。其中 10 个 `exit=1`，均在 `error_stats` 计算
p50/p90/p99 时抛出 `quantile() input tensor is too large`；另 3 个 `exit=-9`
被内核 OOM 杀死（见 §5）。

**根因**：`torch.quantile` 对输入元素数有硬上限。远端实测（torch 2.1.2）：
`2**24 = 16,777,216` 接受，`2**24 + 1` 抛错。而归约类科目的输出规模远超此限
——队列 382 个 unit 中 **234 个（61%）** 输出元素数超过 2²⁴，最大到
2.147e9。也就是说该缺陷若不修，会让本次校准的六成单元失败。

**该缺陷不污染任何已记录结果**，三点理由：

1. 它是**失败即停**（抛异常 → `exit=1` → `control_status=run_error`），不是
   静默降级，不存在"跑完了但数值错了"的行；
2. `calibrate_tolerance` 自身不受影响：它对 **32 个**控制误差取 quantile，
   远低于 2²⁴ 上限，代码未改一字；
3. p50/p90/p99 属**报告统计量**，判定只用绝对容差计数 + NaN/Inf 分支
   （`E3_port对齐清单_B9.md` 第 6 条）。即使这三列缺失也不改判决。

## 4. 修复的 bit-exact 论证

修复由两部分组成，均以"数值与朴素写法逐位一致"为硬约束。

**(a) 超限分位数：`_exact_percentiles`**
用 numpy 的原地 `partition`（introselect）把所需的次序统计量放到其排序位置上，
再用 `torch.lerp` 在相邻两个次序统计量之间插值，秩的算法
（`rank = q·(n−1)`，取下整与上整、权重为小数部分）与 `torch.quantile` 的默认
`interpolation='linear'` 完全相同。因此：

- **不采样**、不近似——返回的是精确次序统计量；
- 插值用的是 torch 自己的 `lerp`，所以结果是"`torch.quantile` 如果接受这个
  输入本会返回的那个数"的**逐位复现**；
- `partition` 在张量自有缓冲区上原地进行，不额外分配。

**(b) 内存融合：`error_stats` 原地重写**
朴素写法在 1.6e9 输出元素上会同时持有约十份 fp64 全量副本，超出预算。重写把
中间量原地融合（`sub_` / `abs_` / `masked_fill_` / `div_(..., out=ref64)`），
但**逐个统计量都作用在与朴素写法完全相同的 fp64 值、完全相同的排列上**：

| 统计量 | 修复后写法 | 逐位一致的理由 |
|--------|-----------|--------------|
| `mean_abs` | `finite_abs.mean()`（单次 torch 归约，未分块） | 值与内存布局都没变 → pairwise 求和树相同 → 末位相同。**决定 3 明令不得改成分块求和** |
| `max_abs` / `num_exceeding` | 对同一 `abs_err` 取 `max` / 计数 | 逐元素比较，与顺序无关 |
| `max_rel` / `mean_rel` | 商落在 `ref64` 缓冲区里（`out=ref64`） | 参与运算的值与顺序不变，仅复用了缓冲区 |
| `p50/p90/p99` | ≤2²⁴ 走原 `torch.quantile`；>2²⁴ 走 `_exact_percentiles` | 见 (a) |
| NaN / Inf 标志 | 改为在**原 dtype** 张量上检查，不再造第二份 fp64 全量副本 | float64 升位对 NaN/Inf 是精确保持的，标志值不可能改变 |

`_owned_float64` 处理了一个必须防的别名陷阱：当输入本已是扁平 CPU float64 时
`.to()` 是 no-op，原地改写会摧毁调用方缓冲区，故此时强制 `clone()`。

**校验**：`_b9_precheck.py` 每次起跑前断言 `QUANTILE_NUMEL_LIMIT == 2**24`
且 `_exact_percentiles` 在位，修复前版本保留为
`b9_seeded_fuzzing.py.bak_quantile_fix` 以便逐行 diff 复核。

## 5. 宿主内存模型（34 B/输出元素）

3 个 unit（L1_P24 fp32/fp16、L1_P33 fp32）以 `exit=-9` 被内核 OOM 杀死。同一次
四道并发还把**关键路径**的 E1 CSE 签认 worker 一起杀了（cgroup `oom_kill`
16→20），这是"B9 必须等关键路径收官后才起跑"这条红线的由来。

修复后按实测建立了显式内存模型，并把它做成**准入闸门**（`queue_state.json`
预留制：unit 先预留估算峰值，装不下就排队，装不下预算的单元强制独占）：

```
参考阶段   = 8·(in_numel + out_numel) + itemsize·out_numel
比较阶段   = (34.0 + 2·itemsize)·out_numel
估算峰值   = max(参考阶段, 比较阶段)
预留量     = 估算峰值 × 1.3
```

- **34.0 B/输出元素**为远端实测常数，在 1.7e7 → 2.0e8 元素区间稳定；
- 安全系数 **1.3** 来自端到端核对：L1_P8 估算 1.9 GB，实测 2.11 GB；
- 并发预算 100 GiB（cgroup 120 GiB 留出余量）；驱动逐 unit 记录
  `unit_peak_rss_gb`，第一波即用它检验上式。

据此的规模分布（400 个 unit）：中位数 4.75 GB，均值 14.61 GB，**最大 84.0 GB**；
预留量 ≥60 GiB 的 46 个 unit 承担了约 46% 的总串行工时，是全量 ETA 的主导项。

**第一波实测校验（2026-07-30 20:28–20:47，4 个单元，全部 `calibrated_ok`）**：

| unit | out_numel | `est_peak_gb` | `unit_peak_rss_gb` | 实测/估算 | wall_s |
|------|----------:|-------------:|------------------:|---------:|-------:|
| `L1_P8__float32` | 4.858e7 | 1.9 | 2.10 | 1.11 | 90.1 |
| `L1_P3__float16` | 1.342e8 | 4.8 | 5.22 | 1.10 | 303.4 |
| `L1_P3__float32` | 1.342e8 | 5.2 | 5.13 | 0.98 | 381.2 |
| `L1_P7__float32` | **1.074e9** | 42.0 | **35.71** | **0.85** | 820.2 |

结论：**34 B/输出元素的模型成立**，四个实测比值 0.85–1.11 全部落在 1.3 安全系数
之内，跨越 4.9e7 → 1.07e9 两个量级、跨越逐元素型与矩阵乘型两种代价体制。
唯一的系统性偏差在大端方向且是**保守的**：`L1_P7__float32` 估算 42.0 GB、实测
35.71 GB，模型高估 18%。叠加 1.3 的预留系数后该单元预留 54.6 GiB 而实际只用
35.7 GB，两个同类单元因此无法在 100 GiB 预算内并行（2×54.6 > 100），尽管实际占用
（2×35.7 = 71 GB）本可容纳。**本次不改安全系数**——第一波尚未跑完，且改动会影响
所有后续单元的准入判定；是否在第一段收官后按实测重标定，另行拍板。

## 6. `calibrated_heavy_tail`：控制自身的假阳性（可披露的测量结果）

**定义**：一个 unit 的 32 次控制跑完、拿到 `calibrated_tol` 后，若仍有控制的
max-abs 误差 > 该容差，记为 `calibrated_heavy_tail`（`calibrated_ok` 反之）。
这意味着**上游规则标定出的容差，连产生它的那批正确内核都无法全部容纳**。

现有 18 个有效 unit 中有 17 个拿到了容差（1 个见 §7），其中 **2 个**为
heavy_tail，且**都是 fp16**：

| unit | 32 次控制误差取值:次数 | p95 | 容差 = p95×1.5 | max | 超容差 |
|------|----------------------|----:|---------------:|----:|-------:|
| `L1_P10__float16`（3D tensor-matmul） | 4.0 : 31, 8.0 : 1 | 4.0 | **6.0** | 8.0 | 1/32 |
| `L1_P16__float16`（matmul, A 转置） | 8.0 : 31, 16.0 : 1 | 8.0 | **12.0** | 16.0 | 1/32 |

**这不是运气不好，是规则与 fp16 粒度的结构性冲突。** 证据是误差取值的离散性：

- 两个 unit 的 32 个误差各自只取 **2 个不同值**，且两值之比恰为 **2.0**
  （log₂ 分别为 2→3 和 3→4）。大规模 fp16 归约的输出落在某个 binade 内，
  max-abs 误差只能取该处 fp16 间距的整数倍，于是误差分布塌缩到一个二进制网格上；
- 一旦 31/32 个控制落在低网格点、1 个落在高网格点，则 p95 = 低网格点，
  而容差 = 1.5×低网格点 **必然**落在两个网格点之间（1.5 < 2.0），
  于是那 1 个高网格点样本**必然**超容差。两个 unit 的 `max/tol` 都精确等于
  **4/3 = 1.3333**，正是 2/1.5；
- 对照 fp32：10 个 fp32 unit 的 32 个误差取 **11–21 个**不同值（分布连续），
  heavy_tail **0 个**。

**假阳性率（现有样本，n 小，仅作行为披露不作总体估计）**

| 口径 | 值 |
|------|----|
| 受影响 unit / 已标定 unit | 2/17 = **11.8%** |
| 受影响 unit / 已标定 fp16 unit | 2/7 = **28.6%** |
| 受影响 unit / 已标定 fp32 unit | 0/10 = **0%** |
| 假阳控制样本 / 全部控制样本 | 2/544 = **0.37%** |
| 每个受影响 unit 内部 | **1/32 = 3.125%** |

**脆弱性补充观察（对论文有用）**：另有 4 个 fp16 unit（`L1_P1`、`L1_P2`、
`L1_P13`、`L1_P17`）的 32 个误差**全部落在同一个网格点**（皆为 8.0）。它们
现在是 `calibrated_ok`，但只要 32 次抽样里出现 1 次落到 8.0 的上一格，就会
立刻变成 heavy_tail。也就是说 7 个 fp16 unit 里有 6 个处在这条分界线附近，
上述 28.6% 并非稳定估计，而是一个**抽样噪声主导**的量——这本身就是"p95×1.5
在 fp16 大归约上不是一个稳定校准规则"的直接证据。

**论文表述口径**：如实报告为 B9 协议在 fp16 大规模归约科目上的**测量到的行为**，
不修正、不排除、不替换规则。B9 因此在这些科目上带有约 1/32 的自身假阳性下界，
这在解读 B9 的 precision 列时必须说明。

## 7. 协议不可判定域（fp16 溢出）列账

`L1_P6__float16`（`6_Matmul_with_large_K_dimension_.py`，K 很大的矩阵乘）：
32 次控制的输出**全部为 Inf**（`outcome_kinds: {"inf": 32}`），即在 fp16 下
正确参考实现本身就溢出。B9 的比较语义先判 NaN/Inf（`E3_port对齐清单_B9.md`
第 6 条），故不存在可用的有限误差样本，无法标定容差，记
`control_status = controls_incomplete`。

**处理规则（决定 5）**：

- 记为 **"协议不可判定"**（B9 在该 (subject, dtype) 上不能给出任何判决），
  **不从分母中排除**；
- 在 Table 6a/6b 的 B9 行中，这类 (subject, dtype) 计入该语料的科目分母，
  B9 在其上一律不得计为检出；
- 与我们自己的 INCONCLUSIVE 纪律同源：**基础设施/协议不能判定 ≠ 被测对象正确**，
  也 ≠ 该科目不存在。

排除它们会系统性虚高 B9 的精度与召回（分母变小、失败样本消失），这正是我们
在 RQ1 里反复强调的 `NO_DEFECT_FOUND ≠ 正确` 的镜像错误。

**判据已落到聚合脚本（2026-07-30）**：`control_status = controls_incomplete`
这个状态名不区分原因，直接拿去统计会把"协议不可判定"与"控制批次残缺"混为一谈。
判据因此写进了 `/root/mk_v2/_b9_aggregate.py:refine_status()` 而不只是本文档：

| 记录值 | 细化后状态 | 条件 |
|--------|-----------|------|
| `controls_incomplete` | `protocol_undecidable_overflow` | `outcome_kinds == {"inf": cases}`（**全批**非有限，fp16 溢出型） |
| `controls_incomplete` | `protocol_undecidable_nan` | `outcome_kinds == {"nan": cases}` |
| `controls_incomplete` | `controls_incomplete_unresolved` | 其余（混合 outcome、批次不足、字段缺失）——**不得**并入不可判定账 |
| `run_error` | `run_error_host_oom` | `exit_code == -9`（§8 的资源边界） |
| `run_error` | `run_error_crash` | 其他非零退出（代码类失败） |

要求"全批"而非"多数"是刻意的：31 个 Inf 里混 1 个有限样本说明参考并非一致溢出，
那是要查的异常，不是协议边界。11 条判据用例由 `--self-test` 断言，聚合时先跑
自测再出账，脚本另落 `b9_calibration_summary.json` 与
`b9_calibrated_tolerances.json`（后者带 `undecidable` / `host_oom` 两份计入分母
的清单与处置规则）。现有 31 行的复算结果与本文件 §6/§7 逐项吻合：
17 个已标定、2 个 heavy_tail（`max/tol` 均 1.333333）、fp16 2/7、fp32 0/10、
`L1_P6__float16` 判为 `protocol_undecidable_overflow`。

## 8. 84 GB 科目：处理规则与论文表述口径

4 个 unit 的估算峰值达 **84.0 GB**（`L1_P38__float32` = L1Norm、
`L1_P39__float32` = L2Norm、`L1_P87__float32`、`L1_P63__float32` 83.7 GB），
预留量 109.2 GiB，超出 100 GiB 并发预算但仍在 120 GiB cgroup 之内，故按准入
闸门**独占尝试**。规则（决定 3）：

1. 独占跑通 → 正常出容差；
2. 独占仍 OOM → **跳过并记录**为"在 120 GiB 宿主预算下超出 B9 可处理域"，
   连同 `est_peak_gb`、`unit_peak_rss_gb`、`exit=-9` 一起入账；
3. **不允许**为让它跑通而把 `mean_abs` 改成分块求和——那会破坏 §4 的 bit-exact
   论证，用一个数值口径已变的结果换取一个"跑完了"的表象。

**论文表述**：这属于**移植的资源边界**，不是 B9 协议的缺陷，也不是我们的实现
缺陷，必须与前两者区分表述。建议脚注口径：

> B9 的 fp64 CPU 参考在输出规模达 2.1×10⁹ 元素的科目上需要约 84 GB 宿主内存；
> 在我们 120 GiB 的执行预算内，有 N 个 (subject, dtype) 单元无法完成标定，
> 逐条列于 artifact。这些单元在所有对比表中计入分母且 B9 不计检出，
> 与 §7 的协议不可判定单元同口径处理。

（N 待第一波与全量跑完后回填；现刻上界为 4 个 unit。）

## 9. 覆盖范围声明（预算匹配公平性）

### 11.3 fd 继承陷阱：从脚本里起常驻进程，不要用 `capture_output`

2026-07-30 20:28:37—21:08:49 的实例：`_b9_chain_trigger.fire()` 用
`subprocess.run(["bash", "resume_b9.sh", ...], capture_output=True, timeout=1800)`
调用一键恢复脚本，而该脚本会起一个**永不退出**的常驻 guard。观测到的后果：

- `resume_b9.sh`（pid 284015）阻塞在 `wchan=do_wait`，其唯一子进程就是 guard
  （284017）；
- **结构性根因**：`cd "$OUT" && LANES=… nohup bash guard_b9_v2.sh > /dev/null 2>&1 &`
  中的 `&` 作用于整个 `cd && …` **AND 列表**，bash 因此 fork 出一个包装子 shell，
  由它在**自己的前台**运行那个永不退出的 guard 并 `wait` 它。同一模式在 guard 起
  lane 时也可见（实测 21:41：guard 284017 之下 289239 / 289243 两个包装子 shell 各
  `do_wait` 于 lane 289241 / 289245）——在那里无害，因为没人去捕获 guard 的输出；
- Python 侧 `communicate()` 要等两个捕获管道 EOF，而管道要等所有写端关闭；
- 30 分钟后 `subprocess.TimeoutExpired` 抛出、未被捕获 → 触发器崩溃 →
  `record_fire()` 从未执行 → `CHAIN_TRIGGER_FIRED` 从未写出 → 依赖该标记判断
  "第一波是否起跑/结束"的下游逻辑全部失效（本次由 keepalive 在 21:00:19 重启触发器
  才恢复看门狗，重启后它走幂等路径 adopt 了在跑的 guard，未起第二波）。

**规则**：任何"从脚本/Python 里启动常驻进程"的地方，
(a) 常驻进程的 `stdout`/`stderr` 必须重定向到**文件**，不得留在管道上；
(b) 调用方不得用 `capture_output=True` 去收一个会起常驻进程的脚本——要么把该脚本的
输出也重定向到文件后再读文件，要么用 `start_new_session=True` + `DEVNULL`；
(c) 下游判据不要依赖"调用方返回后才写出的标记"，要依赖**被调用方自己维护的状态**
（本例中 `queue_state.json` 由 lane driver 自己写，是权威来源，第一段链接器已改为读它）。

### 11.4 终止进程：显式 PID，且不要碰进程组

`pkill -f` / `pgrep -f` 在 SSH 单行命令中会匹配到承载它的 SSH 命令行本身（已造成过
会话被打断与目标未被终止）。终止必须：`/proc` 扫描取 PID → 排除自身与祖先 →
**核对 cmdline 身份** → `os.kill(pid, SIGTERM)`。
**另注**：本次的 `resume_b9.sh`(284015) 与 guard(284017) 共享由已死触发器留下的
`pgrp=sid=276615`，若按**进程组**发信号会把 guard 一起杀掉。只发给单个 PID。

## 12. 内存估计器重标定方案（2026-07-30 拍板；**第一段收官后执行**）

### 12.1 口径

- **只修正估计器的系统性偏差，1.3 安全系数保持不变。** 安全系数防的是"模型没覆盖
  到的效应"，与模型准不准是两件事；本次会话累计 20 次 OOM 击杀、其中一次污染了关键
  路径判级记录，这道防线不能因为模型变准而削掉；
- **时机**：第一段收官后、第二段起跑前。第一段跑动中**不得**改准入判定——否则同一段
  内的单元会在不同规则下被调度，破坏可比性与可复现性。文档须记录"两段所用系数不同"
  这一事实；
- 若重标定后 84 GB 档单元的预留仍超预算（仍需独占），**如实报告，不得为让它们并行
  而降安全系数**。

### 12.2 需要修正什么：残差不是常数倍，而是"固定开销 + 更小的斜率"

现估计器：`ref = 8·(in+out) + itemsize·out`；`cmp = (34.0 + 2·itemsize)·out`；
`est = max(ref, cmp)`。四个实测单元**全部由 `cmp` 支配**，反解其每元素常数：

| unit | out_numel | 实测峰值 | 反解的 `CMP_BYTES_PER_ELEM` |
|------|----------:|--------:|---------------------------:|
| `L1_P8__float16` | 4.858e7 | 2.01 GB | **40.4** |
| `L1_P8__float32` | 4.858e7 | 2.10 GB | **38.4** |
| `L1_P3__float16` | 1.342e8 | 5.22 GB | **37.8** |
| `L1_P3__float32` | 1.342e8 | 5.13 GB | **33.0** |
| `L1_P7__float32` | 1.074e9 | 35.71 GB | **27.7** |

该常数随输出规模**单调下降**（40.4 → 27.7，五个点无一例外），说明真实峰值不是纯比例的，而更像
`peak ≈ a + b·out_numel`（固定开销 a + 更小的斜率 b）。用现有的纯比例模型去拟合，
必然在小端偏低（比值 1.10–1.11）、在大端偏高（0.85）——这正是观测到的形状。

### 12.3 拟合方法（**上包络拟合，不用最小二乘**）

决定 1 要求"任何单元的新估算不得低于其实测峰值"。最小二乘按定义会让约一半的点落在
拟合线上方，必然违反该要求。因此采用**上包络（约束）拟合**：

> 求 `a, b` 使 `Σ_i (a + b·out_i − actual_i)` 最小，**约束** `a + b·out_i ≥ actual_i`
> 对所有已观测单元成立。

这是一个二变量线性规划，等价于取所有点的上凸包下边界；实现上可直接遍历点对求解，
无需求解器。它把决定 1 的回归门槛做成**结构性满足**而非事后检查。分 dtype 各拟合一组
`(a, b)`（fp32 / fp16 的 `2·itemsize·out` 项不同），并保留 `ref` 分支不动（尚无
`ref` 支配的实测单元，无依据修改）。

### 12.4 回归验证（执行时必须逐条输出）

1. 对**每个**已完成单元打印 `新估算 / 实测峰值`，要求全部 **≥ 1.0**（上包络保证），
   并报告最小余量；
2. 报告 `新预留 = 新估算 × 1.3` 与实测峰值的比值，要求最大比值仍留有余量
   （现观测最大 **1.17**，出现在最小的 fp16 单元 `L1_P8__float16` 上，余量 0.13；
   小单元比值最高与"固定开销"假设一致，也说明重标定的收益主要在大端）；
3. 任何单元的新估算低于其实测峰值 → **视为拟合失败，回退旧系数并上报**；
4. 报告重标定对调度的影响：`(a) 新预留下 <60 GiB 的单元数`、`(b) 84 GB 档单元的新
   预留是否仍超 100 GiB 预算（即是否仍需独占）`、`(c) 第二段 ETA 的变化`。

### 12.5 现刻可预判的量（不构成结论）

以 4 个点粗估斜率约 35 B/输出元素、固定开销约 0.5 GB。若该形状成立，84 GB 档
（`L1_P38/39/87/63`，2.147e9 输出元素）的新估算约 `0.5 + 35×2.147e9/2³⁰ ≈ 70 GB`，
新预留约 91 GiB —— **仍小于 120 GiB cgroup 但大于 100 GiB 并发预算的一半，因此这些
单元仍必须独占**。四个点不足以支撑任何决定，此处只说明"重标定不太可能让 84 GB 档
变成可并行"，与决定 1 最后一句的预期一致。

## 13. 通用规则：**B9 标定只对已冻结（人工审核签认）的契约执行**

### 13.1 规则与依据

> **规则（通用，非 L3 特例）**：一个 (subject, dtype) 单元只有在其契约**已通过双人
> 审核并冻结**之后，才可以进入 B9 控制标定队列。草稿契约（`"draft": true`）不得
> 标定。

依据不是调度便利，而是**数据有效性**：`calibrated_tol` 是后续**所有** E3 判决的输入。
契约的输入域（shape / dtype / 取值范围 / 变维 / 确定性条款）决定了 32 次控制跑在什么
输入上；审核若改动其中任何一项，那批容差就不再对应最终科目集——

1. 已花的 GPU 工时作废；
2. 更糟的是，作废的容差**仍留在盘上**，可能被后续步骤当作有效标定误用，等于把
   一个未定版的输入域烧进判决基线。

这类错误不会报错、不会崩溃，只会静默地产出"看起来完整"的判决表，因此必须用流程
杜绝，而不是靠事后核对。

**已完成的 400 单元档如何解释**：当前在跑的 200 任务（L1+L2）契约同样是草稿
（`contracts_c2c3c5_draft.freeze.json` 的 `"draft": true`）。这一批的处理沿用
§10 第 5 条：**契约冻结后必须复核 `contract_sha256` 是否变动**，凡变动的任务其容差
作废重标。新规则从 L3 这一批起前置执行，避免重复这笔风险敞口。

### 13.2 L3 的 100 个单元：**第三批，签认后单独排**

拍板结论：L3 的 100 个单元**既不进第一段、也不进第二段**，作为**审核签认后的第三批**
单独排期。理由有两层：

- **风险面**：50 份 L3 契约现为未审草稿（见 §13.1）；
- **收益面不足以抵消风险**：L3 单元很便宜——meta + 真实前向实测的尺寸画像为
  `est_peak_gb` 中位 **0.04 GB**、最大 **42.00 GB**（`L3_P17` SqueezeNetFireModule，
  输出 1.074e9 元素），**≥60 GiB 预留的单元数为 0**。既然便宜、
  随时可跑，就没有任何理由为"顺路"而冒契约变更的风险提前跑。

## 14. 归属制 brake 协议（`_b9_brake.py`，2026-07-30 拍板并部署）

### 14.1 它替代了什么，为什么这是"消除失败类别"而不是"降低概率"

原机制是**一个不署名的文件** `PAUSED_FOR_SIGNOFF_RERUN`。任何想拿回 GPU 的组件都无法
知道 brake 是谁放的、还需不需要，只能**猜**。已部署的链式触发器的猜法是轮询关键路径
进程：连续两次干净轮询就解除。这是概率性的——

- 一方的 worker 若有超过两个轮询周期的空档，它的 brake 会被静默解除；
- 而 lane **只在单元之间**尊重标记，所以解除后 lane 可能起一个跑满 4 小时的大单元，
  与那一方重叠占用 GPU。当初正是这种重叠把关键路径的判级记录 OOM 掉的。

**缩小轮询窗口只能降低概率，不能消除失败类别**，因为对方的空档长度可以任意长。
2026-07-30 21:36:21 实测到该失败：触发器在审计 worker 空档中解除了审计方的 brake
（那一次因为审计恰好已收官而无害，但机制本身不成立）。

协议把归属写进 brake 本身：

1. **每个需要抑制 B9 的一方各自放置署名标记** `brakes/BRAKE_BY_<owner>`，内容记录
   放置者、时间、原因、预期释放条件；
2. **只有放置者自己释放**（或人工显式释放）；任何自动化不得移除他人标记——**没有
   需要猜的东西**；
3. **lane 起跑的条件是"不存在任何 brake"**，不是"某个特定标记不存在"。多方可并存
   持有，**最后一个释放者才放行**，天然无竞态；
4. 历史标记 `PAUSED_FOR_SIGNOFF_RERUN` **既不忽略也不接管**：一份不是我们写的该文件，
   在其存在期间被计为持有者 `unknown_legacy`，并**按其放置者的预期方式释放**——由该
   放置者删除文件。我们只记录观测（`brakes/observed_foreign.jsonl`），不改其内容。

**为什么是"追踪"而不是"接管"**：协议的第一版把外部文件转成自己的标记并声明为
"仅人工可释放"。那在两个方向上都错了——它改写了别人的文件，而且把一个放置者本会自行
释放的 brake 变成了需要人工的，一旦放置者释放，B9 反而会被卡死。实测中这一版确实
改写过审计方 21:45:48 的标记文本（brake 始终在位、未被释放，故无安全影响），随后按
`original_text` **逐字节还原**（217 B，sha256 `95e4043b…`）并撤销了所属权声明。
定版规则：**外部文件在位时绝不写派生文件，也绝不声明拥有它。**

### 14.2 与已部署 guard / lane 的衔接（不改动它们）

已部署的 guard 与 lane driver 仍然只读 `PAUSED_FOR_SIGNOFF_RERUN`。协议因此把该文件
当作持有者集合的**派生视图**：只要我们有任一持有者就写出它（首行为哨兵
`#b9-brake-derived-v1`，并列出全部持有者与释放条件），持有者清空后归档移除。
外部文件在位时不写。审计过的 guard / lane 代码**一行未改**。

### 14.3 失败模式：崩溃即"保持刹车"，绝不"释放刹车"

brake 存在于**文件**而非进程中；`sync()` 只有在**确实观测到持有者集合为空**时才移除
派生文件，且**没有任何退出清理路径**。因此监管进程崩溃 → brake 全部保持有效 →
lane 保持停止。另有两个独立证据判定"派生文件是否我们写的"：侧记文件（精确，但进程
崩溃可能丢）与文件内哨兵（任何情况都在，且外部 `pause_b9.sh` 文本不可能含它）。
哨兵这一路是为了避免**自造死锁**：只有侧记时，丢失侧记会让我们自己的 brake 看起来
像外部的，从而需要人工才能清除。

### 14.4 用法

```
python /root/mk_v2/_b9_brake.py status
python /root/mk_v2/_b9_brake.py hold <owner> --reason "..." [--release-when "..."]
python /root/mk_v2/_b9_brake.py release <owner> [--actor human]
```

`hold` 强制要求 `--reason`——不写原因的 brake 正是本协议要消灭的东西。
