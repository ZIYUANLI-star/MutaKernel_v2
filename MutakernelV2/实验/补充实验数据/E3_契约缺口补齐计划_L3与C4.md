### 1.4 两处必须提前记录的口径后果

**(a) B9 port 的单张量输出限制会吃掉一部分 L3 单元。**
`scripts/run_e3_external.py:_run_b9_case()` 对非单张量输出直接返回
`INCONCLUSIVE`（"B9 port supports single-tensor outputs"）。L3 里 LSTM/GRU 的
`Hn`/`Cn`/`Bidirectional` 变体（`L3_P34`、`L3_P36`–`P38`、`L3_P40`–`P42`）与
`Mamba2ReturnFinalState`（`L3_P49`）等返回元组，落在 port 的不可判定域。
处置与 `E3_B9校准决定与限制说明.md` §7 同源：**计入分母、B9 不计检出、逐条列账**，
由已部署的 `_b9_aggregate.py` 归类，不得静默排除。数量待 A5 探针确认。

**(b) 现有 ETA 模型对 L3 不成立。**
`_b9_resume_prep.estimate()` 用 `32 × (in_numel + out_numel) / rate` 建模，
`rate` 的两个锚点都来自 L1/L2 的逐元素与 fp64 matmul 体制。L3 的代价主导项不是
张量元素数而是**fp64 CPU 上的卷积/循环栈深度**：VGG16 在 batch 10、224² 下前向
约 3×10¹¹ fp64 FLOP，与其 10³ 量级的输出元素数完全脱钩。因此 L3 档的 ETA
**不得用现有模型外推**，必须以 A5 的 4 单元实测为锚。§4 给出的 L3 ETA 已按此标注。

### 2.2 草稿的实际信息量（这是真正需要补的部分）

对 184 行逐条统计：

| 指标 | 值 | 含义 |
|------|----|------|
| 有至少一个字面 shape 的任务 | **87 / 184** | 另 97 个任务的 tensor 构造形状不是字面量（来自变量、循环、配置），静态 AST 取不到 |
| 完全没有 tensor_hints 的任务 | 7 / 184 | 测试段没有可识别的张量构造调用 |
| `signature` 为空 | **184 / 184** | 提取器读 `record["func_inputs"]`，而 `TritonBench_G_v1.json` 的记录字段是 `file/repo/simp_instru/comp_instru/output/difficulty/star`，**没有 `func_inputs`**。这是提取器与该 manifest 版本的字段错配，需要修正为读 `comp_instru`/`output` |

即：草稿证明了"184/184 都被扫过、零失败"，但作为契约它**只覆盖不到一半任务的

### 2.3 C4 的实质阻塞：TritonBench-G 不提供独立参考实现

逐文件核查 `external/C4_tritonbench/data/TritonBench_G_v1/`（184 个 `.py`，
本地完整）的结构：每个文件 = Triton kernel + Python wrapper + 一个 `test_*()`
函数，文件末尾以 `result_gold = test_xxx()` 收尾。其官方评测
（`EVAL/eval_G/{0_call_acc,1_exe_acc,2_efficiency}.py`）判的是**执行准确率与
性能**，"gold" 就是被测文件自己跑出来的结果。

因此：**C4 语料里没有任何可作为差分对照的独立参考实现。** 这对所有预算匹配行
同等成立——B1u/B7/B8/M-full/M-dir 与 B9 都需要一个 reference 才能判 PASS/FAIL，
B9 更需要一个可在 fp64 CPU 上重放的参考。这不是 B9 的问题，也不是契约草稿的
问题，而是 C4 这个语料的接口性质。

### 2.3.1 选定方案：P2-随机（预注册均匀随机子样本 + 自撰参考）

**2026-07-30 拍板：取 P2 但抽样必须是预注册均匀随机抽样，不取 P1 全量自撰。**
否决 P1 的理由是可行性：60–120 人时对单人研究者是两三周纯人工。曾考虑并被否决
的其余路径备查：P1 全量自撰（成本不可行）、P3 降为纯 sanitizer 语料（差分行仍空，
缺口只缩小不消除）、P4 放弃 C4（损失唯一 Triton 语料，直接削弱跨语言泛化主张）。

**关键区分：选择偏差只在便利抽样下成立，不在概率抽样下成立。** 本计划早先设想的
"只取 87 个有字面 shape 的任务"正是便利抽样，其偏差是可量化的——按 manifest 的
`difficulty` 字段交叉统计：

| difficulty | 全语料任务数 | 其中有字面 shape | 便利框内占比 vs 全语料占比 |
|-----------:|------------:|----------------:|--------------------------|
| 1 | 3 | 2 | 2.3% vs 1.6% |
| 2 | 27 | 15 | 17.2% vs 14.7% |
| 3 | 65 | 36 | 41.4% vs 35.3% |
| 4 | **84** | **32** | **36.8% vs 45.7%** |
| 5 | 5 | 2 | 2.3% vs 2.7% |

即便利框会把最难的一档（difficulty 4，占语料 45.7%）压到 36.8%，正是"难任务缺
字面 shape"造成的系统性偏斜。均匀随机抽样消除的就是这一项。

### 2.3.2 抽样协议（预注册，2026-07-30 定案：**n = 60，按 difficulty 分层**）

**(1) 抽样框**：全部 **184** 个任务，不是 87 个有字面 shape 的任务。缺字面 shape

**(2) 样本量与停止规则（预注册，不得依赖结果）**

- 样本量 **n = 60**；
- 停止规则逐字预注册为：**"撰写至预先声明的 n = 60 份参考为止；若人时预算先于
  n = 60 耗尽，则在耗尽时停止"**。除这两个条件外不得停止，**尤其不得因为已写出的
  结果好看或难看而停**；
- 提前停止时以实际完成份数 m 为样本量，按 (6) 的性质其 π_i = m/184，估计量照常
  成立，只需在 freeze 里记录停止时刻、原因（"预算耗尽"）与 m。

**(3) 分层与配额（按 manifest 实际分布计算，非估计）**

分层变量为 manifest 的 `difficulty` 字段。**该字段实际有五档而非四档**，实测分布
与 n = 60 的比例分配如下（`TritonBench_G_v1.json`，184 条，
sha256 `78d730f062d6c6ee1c369da0df3bd98b7039c192313600b578ecda9a55d8b0a2`）：

| difficulty | N_h | 精确配额 N_h·60/184 | 向下取整 | 余数 |
|-----------:|----:|-------------------:|--------:|-----:|
| 1 | 3 | 0.9783 | 0 | 0.9783 |
| 2 | 27 | 8.8043 | 8 | 0.8043 |
| 3 | 65 | 21.1957 | 21 | 0.1957 |
| 4 | 84 | 27.3913 | 27 | 0.3913 |
| 5 | 5 | 1.6304 | 1 | 0.6304 |
| **合计** | **184** | **60.0000** | **57** | **3.0000** |

取整只能分掉 57 个名额，余 **3** 个。余数分配规则有两种，**必须预注册选定其一**：

| 规则 | 配额 n_h（d1…d5） | 实际 π_i = n_h/N_h | 与目标 60/184 = 0.326087 的偏离 |
|------|------------------|-------------------|------------------------------|
| **A 最大余数法**（确定性） | 1 / 9 / 21 / 27 / 2 | 0.3333 / 0.3333 / 0.3231 / 0.3214 / **0.4000** | −1.4% … **+22.7%**，**π_i 不再是常数** |
| **B 余数随机化**（种子化系统抽样分配那 3 个名额，各层入选概率 = 其余数） | 期望 0.978 / 8.804 / 21.196 / 27.391 / 1.630，总数恒为 60 | **0.326087（全部相同）** | **0** |

**采用规则 B。** 理由是决定 2 的前提就是"π_i 仍等于 n/184、等概率性不变"，而
规则 A 做不到这一点：difficulty 5 只有 5 个任务，多给一个名额就把它的纳入概率抬到
0.40（超出目标 22.7%），difficulty 4 则被压到 0.3214。规则 B 把 3 个余数名额交给
一次种子化系统抽样（各层入选概率等于其余数，余数之和恰为 3.0，故必然分出且只分出
3 个名额），于是每个任务的纳入概率**精确**等于 60/184，总样本量**精确**为 60，
唯一的随机成分是各层实际抽到 `floor_h` 还是 `floor_h + 1` 个。规则 B 的这一条随机
化本身也在预注册之内（同一种子、同一脚本），因此仍可逐条复现。

作为对照记录（不采用）：若把两个微型层并入相邻层做三层分层
（low = d1+d2 = 30、mid = d3 = 65、high = d4+d5 = 89），最大余数法给出配额
10 / 21 / 29，π_i 落在 0.3231…0.3333（最大偏离 +2.2%），比规则 A 好但仍非常数。
之所以不采用，是因为规则 B 在保留 manifest 原生五档分层的同时把偏离降到 0。

**(4) π_i 恒定性的验证方式（可被审稿人重跑）**

预注册脚本必须输出并落盘三项，供独立复核：

1. 每层的 `N_h`、`floor_h`、余数、以及规则 B 下的入选概率；
2. 每个任务的 `pi_i` 字段（规则 B 下应逐条等于 `60/184`，脚本断言
   `max|pi_i − 60/184| < 1e-12`，不满足即中止且不产出样本）；
3. 用同一种子重跑 1000 次分配、统计各层被抽到 `floor_h + 1` 的经验频率，与其
   余数比较（蒙特卡洛自检，偏差应在抽样误差内）。这一项证明的是分配机制本身没写错，
   与真实抽样是两件事，只在预注册阶段跑一次。

**(5) 可复现性凭证（四项，全部写入 freeze 文件）**

| 凭证 | 值 / 来源 |
|------|----------|
| 随机种子 | **42**（与 E0/E1 协议常量一致） |
| 抽样脚本内容哈希 | 脚本文件的 sha256，执行时现算并写入 |
| manifest sha256 | `78d730f062d6c6ee1c369da0df3bd98b7039c192313600b578ecda9a55d8b0a2`（184 条） |
| 置换后的任务顺序 | 被抽中的 60 个 `task_id` **按撰写顺序**的完整有序列表，连同每条的 `difficulty`、`pi_i`、层内序号一并落盘 |

给定这四项，任何人无需访问我们的机器即可逐条复现"抽中了哪 60 个、以什么顺序写"。

**(6) 撰写顺序与前缀性质**

分层抽样先定出这 60 个任务，再用同一种子对这 60 个做一次**均匀随机置换**，按该顺序
撰写。于是任意长度 m 的前缀满足

> π_i(前缀 m) = P(被抽中) × P(落在前 m 位) = (60/184) × (m/60) = **m/184**，对每个
> 任务都相同。

即前缀仍是精确等概率样本，"写到第 40 份"就是合法的 m = 40 样本。需要如实记录的
代价是：前缀只保证等概率，**不保证按 difficulty 比例平衡**（层平衡是整个 60 份
写完才成立的性质）。若提前停止，freeze 里同时记录前缀内各层的实际计数，方差按
实际构成计算，不按目标配额计算。

**(7) 不可判定任务不重抽**

超出 B9 port 单张量输出限制的任务（返回元组 / 原地改写 / 返回 None）**不重抽、
不替换**：按既定口径计入分母、B9 不计检出，由 `_b9_aggregate.py` 归类列账。
替换它们会破坏等概率性——这正是"用可判定性做筛选"的便利抽样。

**(8) 估计量**

纳入概率逐条落盘后直接接入蓝图 §5.1.5 已有的 Horvitz–Thompson / Hájek 估计量，
**复用同一套口径，不另造**。聚类单位沿用蓝图既定的"底层 benchmark 任务标识"；
语料含 61 个不同上游 repo，repo 作为方差诊断的第二聚类层记录，但不改变抽样设计。

### 2.3.3 自撰参考的自检回路（`result_gold` 绝不可当 oracle）

TritonBench 文件末尾的 `result_gold = test_xxx()` 是**被测内核自己**跑出来的。
若内核有缺陷，gold 就是带缺陷的；拿它当 oracle 会把缺陷编码进我们的参考，然后
所有验证器都判 PASS——这正是 RQ1 指控 de-facto 标准的那个错误。协议：

| 情形 | 处置 |
|------|------|
| 参考与 gold 在 gold 自带输入上**一致** | 仅记为**冒烟通过**。不构成参考正确性的证明，也不降低该任务被审核的要求 |
| 参考与 gold **不一致** | **必须人工判定**归因：(a) 参考实现写错 → 修正并重跑冒烟，记录修正次数；(b) **内核本身有缺陷** → 这本身是一项发现，单独记入 C4 的缺陷池与审计队列，并在 artifact 里给出可复现的反例 |
| 无法判定归因 | 记 INCONCLUSIVE，任务保留在分母中，不为此重抽 |

**(b) 类的计数必须单独报告**：它是"用独立参考替换自证 gold"这一步带来的净增
发现，与验证器之间的比较是两件事，不得混入 Table 6a 的任何单元格。

### 2.3.4 参考实现的独立可复核性

每份参考随记录落盘：作者、撰写日期、依据（该任务 `simp_instru` / `comp_instru`
的语义描述段落 + Triton 源码中的 wrapper 签名）、审核人、冒烟结果、修正历史。
审核与契约的双人审核合并进行（同一份 diff 同时看参考语义与契约边界条款），
避免两轮开销。参考源码随 artifact 发布。

#### 2.5.1 两条必须写入论文口径的结论

以下两条是本次功效分析的直接产物，**导师确认要在论文中显式披露**，不得因为难看
而略过——审稿人自己会算出来，我们先讲清楚比被问出来好。两条均已同步写入蓝图
Table 6a 的缺口标注段（v1.14）。

**结论 1：绑住 C4 列精度的是抽出的缺陷池大小，不是参考份数。**
缺陷池 ≈ n × q × 1.4，在 q ≈ 0.14 下 n = 60 只给约 **12 个确认缺陷**。覆盖率是
"检出数 / 缺陷池"，分母只有 12 时区间必然宽（±20 pts）。**这与抽样设计无关**：
换成简单随机、换成分层、甚至换成 184 个任务的普查，都只是把 q 乘上一个更大的
任务数，改变不了"C4 的缺陷密度决定了该列分母"这一事实。因此该列的区间偏宽应被
读作**语料规模与缺陷密度的联合后果**，而不是抽样方式的缺陷或我们偷工减料。

**结论 2：逐语料显著性检验在任何可行的 n 下都拿不到。**
按 §2.5 的配对假设，检验需要约 8 个不一致对；q = .139 下这要求 n ≳ 120，即接近
普查。**但这与蓝图既有设计并不冲突**：蓝图 §5.3 与 Table 6a 题注本就规定
"per-cell 区间进 artifact、显著性检验只在聚合层（Table 6b）计算"，逐语料从来只承担
描述性角色。因此 n 是按**描述性估计的精度 + 对聚合缺陷池的贡献**选的，不是按
逐语料显著性选的；C4 子样本的缺陷会并入聚合池参与 Table 6b 的检验，在那一层它是
有贡献的。
